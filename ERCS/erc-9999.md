## Abstract

This ERC defines an onchain registry for *value records* of agentic resources. A value record binds an ARD entry (as defined by the Agentic Resource Discovery specification, v0.91) to an onchain anchor — a token-bound executable skill, a token-bound task tender, an address-anchored agent identity, or an ARD registry endpoint — and to the address that controls it. Every record is a valid ARD entry, and every resolver that serves records is a conformant ARD registry, so agents and agent users outside Web3 discover and consume onchain value through ordinary ARD search. Authority over a record belongs to an address, never to a domain; a domain is an endorsement an address can collect. Records are identified by their anchor; ARD URNs are aliases.

## Motivation

TBD. Outline:

- ARD answers *what exists and who says so*; it defines no price, payment, settlement, escrow or credit, has no demand side, and roots trust in domain ownership.
- The agent economy needs the complementary half: *what it is worth, who stands behind it, how it settles*. These are exactly the concerns of token-bound executable skills (supply side), token-bound task tenders (demand side) and address-anchored agent identity (the party).
- Value root = settlement root: any party that gets paid in the agent economy already holds an address (the payee of an HTTP 402 payment is an address). Rooting value in the address adds nothing a publisher does not already have.
- Every ARD entry is a dormant value record until a controlling address anchors it. Domain-only publishers remain discoverable; they are simply not priceable.
- Two-sided discovery: a `task` record is the first ARD entry whose reader is a supplier looking for work rather than a consumer looking for a tool.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174).

### 1. Definitions

- **ARD entry**: an entry object as defined by the Agentic Resource Discovery specification (`identifier`, `displayName`, `type`, exactly one of `url` or `data`, optional members). This ERC does not restate that specification; the subset it relies on is vendored under `../assets/eip-9999/vendor/ard/` with its license.
- **Record**: an onchain value record = kind + anchor + descriptor hash + canonical URN + status.
- **Anchor**: the identity of a record. A token anchor is a CAIP-19 asset identifier; an address anchor is a CAIP-10 account identifier. Onchain, an anchor is `(chainId, target, id)`; `id` is `0` for address anchors.
- **Controller**: the address with authority over an anchor, derived by the kind adapter at call time and never stored.
- **Descriptor**: the publisher-authored ARD entry, including the authored `value:` members. Its hash is stored onchain.
- **Resolver** (gateway): software that reads registry events and domain manifests, computes derived facets, and serves records through the ARD registry interface.
- **Binding**: the relation between a domain and an address, with states `unbound`, `claimed`, `verified`, `contested`.
- **Level**: `L0` dormant, `L1` anchored, `L2` backed.

### 2. Kinds

A kind is a *value posture*: the side of a trade an entry occupies. The ARD `type` is the *payload format*. The two are orthogonal. A kind identifier is `bytes32 kindId = keccak256("ard-onchain.kind.<name>")`.

| kind | posture | anchor | controller |
|---|---|---|---|
| `skill` | offer (supply side) | token-bound executable skill token (CAIP-19) | current token owner |
| `task` | tender (demand side) | token-bound task tender token (CAIP-19) | tender creator / owner |
| `agent` | subject | agent identity address (CAIP-10), `id` = 0 | the address itself |
| `registry` | index | gateway operator address or registry contract (CAIP-10) | the target |

A registry instance MUST support the four kinds above. New kinds MUST correspond to new postures; a new payload format MUST NOT introduce a kind. Kind names `assertion`, `policy` and `market` are reserved and not defined by this ERC.

### 3. Anchors and identifiers

- `recordId = keccak256(abi.encode(block.chainid, target, id))`. One anchor has at most one record; registering an existing anchor under a different kind MUST revert.
- Anchors MUST be on the same chain as the registry instance.
- Equality of records is decided by anchor only. ARD URNs are aliases.
- **Canonical URN**: the URN supplied by the controller. It is valid only while the binding between the URN's publisher domain and the controller is `verified` and the domain manifest contains an entry with that URN. Otherwise the record has gateway aliases only.
- **Gateway alias**: `urn:air:<gateway-domain>:onchain:<anchor-encoding>`, published by the gateway in its own manifest. TBD: anchor encoding.

### 4. Descriptor

- Authored members (hashed): the ARD base members plus `value:kind`, `value:controller`, `value:terms`, `value:settlement`, `value:provenance`, `value:credit`, `value:dispute`, `value:eligibility`, `value:registration`, `value:indexes`.
- Resolved members (never hashed, added by resolvers): `value:anchor`, `value:binding`, `value:level`, `value:status`, `value:aliases`, `value:canonical`, `value:registry`, `value:descriptorHash`.
- `descriptorHash` = SHA-256 over the JSON Canonicalization Scheme ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)) serialization of the authored descriptor. A resolver that fetches a descriptor whose hash does not match MUST NOT serve it as consistent.
- The `value` prefix expands to `https://eips.ethereum.org/assets/eip-9999/ns#`; the context document is `../assets/eip-9999/schemas/value-context.jsonld`.

### 5. Domain binding

- An address claims a domain onchain (`claimDomain`, or `claimDomainBySig` with an [EIP-712](./eip-712.md) signature, verified for contract accounts through [ERC-1271](./eip-1271.md)). The registry records claims and never adjudicates them. Domains are normalized (lowercase, no trailing dot, punycode) before hashing.
- A domain acknowledges an address off-chain: its `/.well-known/ard.json` contains either an entry whose `value:controller` is the address, or a top-level `value:controllers` array containing it.
- Binding states are computed by resolvers: `unbound` (no claim), `claimed` (claim, no acknowledgment), `verified` (claim and acknowledgment), `contested` (several claims; an acknowledged one is `verified`, the rest `claimed`).
- A record whose controller has no verified binding to the publisher domain of its URN is served with `value:binding` = `third-party`.
- Loss of acknowledgment demotes `verified` to `claimed`; canonical URNs under that domain become stale aliases. A binding that returns does not retroactively authorize statements made during the gap.

### 6. Levels and status

- `L0`: no record. `L1`: record exists with status `Active`. `L2`: the kind adapter reports the anchor as backed.
- Record status: `Active`, `Suspended`, `Retired` (terminal).

### 7. Kernel interface

```solidity
interface IARDOnchainRegistry /* is ERC-165 */ {
    enum Status { None, Active, Suspended, Retired }

    struct Record {
        bytes32 kind;
        address target;
        uint256 id;
        bytes32 descriptorHash;
        string  descriptorURI;
        string  urn;
        Status  status;
        address registrant;
        uint64  updatedAt;
    }

    event Registered(bytes32 indexed recordId, bytes32 indexed kind, address indexed target, uint256 id, address registrant, bytes32 descriptorHash, string descriptorURI, string urn);
    event DescriptorUpdated(bytes32 indexed recordId, bytes32 descriptorHash, string descriptorURI, string urn);
    event StatusChanged(bytes32 indexed recordId, Status status);
    event DomainClaimed(bytes32 indexed domainHash, address indexed controller, string domain);
    event DomainReleased(bytes32 indexed domainHash, address indexed controller);
    event KindRegistered(bytes32 indexed kind, address adapter, string uri);

    function register(bytes32 kind, address target, uint256 id, bytes32 descriptorHash, string calldata descriptorURI, string calldata urn) external returns (bytes32 recordId);
    function updateDescriptor(bytes32 recordId, bytes32 descriptorHash, string calldata descriptorURI, string calldata urn) external;
    function setStatus(bytes32 recordId, Status status) external;

    function claimDomain(string calldata domain) external;
    function claimDomainBySig(string calldata domain, address controller, uint256 nonce, uint256 deadline, bytes calldata signature) external;
    function releaseDomain(string calldata domain) external;

    function recordIdOf(address target, uint256 id) external view returns (bytes32);
    function recordOf(bytes32 recordId) external view returns (Record memory);
    function controllerOf(bytes32 recordId) external view returns (address);
    function backed(bytes32 recordId) external view returns (bool);
    function claimsOf(bytes32 domainHash) external view returns (address[] memory);
    function hasClaim(bytes32 domainHash, address controller) external view returns (bool);
    function kindAdapter(bytes32 kind) external view returns (address);
    function nonces(address controller) external view returns (uint256);

    function supportsInterface(bytes4 interfaceId) external view returns (bool);
}
```

- `register` MUST revert unless the kind has an adapter, `adapter.exists(target, id)` is true, and `msg.sender == adapter.controllerOf(target, id)`.
- `updateDescriptor` and `setStatus` MUST revert unless `msg.sender` is the current controller. `Retired` is terminal.
- `controllerOf` and `backed` MUST be forwarded to the kind adapter; the registry MUST NOT cache controllers.
- The registry MUST implement [ERC-165](./eip-165.md) `supportsInterface` for the interface above.

### 9. Resolver (gateway) conformance

A resolver that serves records MUST be a conformant ARD registry: it MUST implement the search endpoint with the three federation modes, SHOULD implement the explore endpoint, MAY implement the listing endpoint, and MUST publish its own manifest containing at least one entry of type `application/ai-registry+json` describing itself. Served records MUST carry `value:anchor` and `value:descriptorHash` so that any client can verify them against the chain or against a second resolver.

## Backwards Compatibility

- Every record is a valid ARD entry; a registry that ignores the `value` namespace sees ordinary entries.
- Existing ARD manifests are dormant (`L0`) records; nothing changes for them until an address anchors them.
- No change is required to the anchored token, tender or identity contracts; adapters read their existing interfaces.
